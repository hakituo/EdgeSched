# 6. Evaluation

## 6.1 实验设置

我们在具有代表性的边缘设备环境中评估 EdgeSched，以验证其资源管理能力、负载下的稳定性以及故障恢复机制。

**硬件环境**:
- **平台**: WSL2 (Ubuntu 24.04-E) 运行于 Windows 11
- **CPU**: AMD Ryzen 9 8940HX (16 Cores, 32 Threads)
- **RAM**: 32GB DDR5
- **GPU**: NVIDIA GeForce RTX 5070 Laptop (8GB VRAM)
- **存储**: NVMe SSD

**软件栈**:
- **Python**: 3.10.19 (WSL2 环境)
- **框架**: PyTorch 2.x, asyncio
- **LLM 后端**: llama.cpp，运行 `qwen2.5-7b-instruct-q4_k_m.gguf` (4-bit 量化, 模型占用约 4.7GB)
- **图像后端**: Stable Diffusion WebUI Forge (运行 SDXL Turbo, 显存需求约 6.7GB)

**评估指标**:
- **TTFT (首字延迟)**: 从发出请求到生成第一个 token 的时间延迟。
- **服务中断时间**: 资源迁移过程中 LLM 服务无法响应的时长。
- **恢复时间**: 从进程重启到任务状态完全恢复的时间。
- **吞吐量**: 并发负载下每秒完成的任务数。

---

## 6.2 资源迁移与共存

EdgeSched 的核心能力是支持内存密集型的 LLM（常驻任务）与图像生成（突发任务）在单张 8GB 显卡上共存。

### 6.2.1 迁移延迟与用户体验

我们测量了完整迁移周期内的系统行为：(1) LLM 在 GPU 上运行，(2) 图像任务抢占（LLM 卸载到 CPU），(3) 图像任务执行，(4) LLM 回迁至 GPU。

**表 1: 资源迁移性能**

| 指标 | 数值 (ms) | 说明 |
| :--- | :--- | :--- |
| **GPU TTFT** | 26.5 | LLM 常驻 GPU 时的基准延迟 |
| **CPU TTFT** | 198.2 | LLM 运行在 CPU 时的降级延迟 |
| **迁移耗时** | 1814.7 | GPU→CPU 卸载的端到端耗时 |
| **最大卡顿 (迁移)** | 2242.3 | 卸载过程中用户感知的最大服务停顿 |
| **回迁耗时** | 2137.9 | CPU→GPU 恢复的端到端耗时 |
| **最大卡顿 (回迁)** | 291.6 | 恢复过程中用户感知的最大服务停顿 (热切换) |

**分析**:
- **无缝恢复**: 回迁卡顿 (291.6 ms) 显著低于总回迁耗时 (2137.9 ms)。这验证了我们的 **原子热切换 (Atomic Hot-Swap)** 策略：CPU 实例持续服务，直到 GPU 实例预加载完成才进行切换。
- **可接受的降级**: 虽然 CPU TTFT (198.2 ms) 慢于 GPU 约 7.5 倍，但仍处于交互可用的范围内 (< 200ms)，保证了图像生成期间 LLM 服务不中断。
- **迁移成本**: 初始卸载时的卡顿 (~2.2s) 是资源竞争的主要代价。这是移动 ~4GB 数据的物理约束，但 EdgeSched 确保这仅在突发任务开始时发生一次，而非影响每个 token。

### 6.2.2 队列背压与互斥

为了验证资源隔离，我们在 LLM 会话活跃期间提交了并发的图像生成任务。

- **队列等待时间**: 第二个图像任务在队列中等待了 **22,797.6 ms**。
- **行为表现**: 系统正确强制执行了 GPU 严格互斥。第二个任务没有导致 OOM (显存溢出) 崩溃，而是排队等待直到第一个任务完成并释放资源。
- **稳定性**: 在整个图像生成队列处理期间，LLM 服务始终保持响应 (在 CPU 上)。

---

## 6.3 崩溃恢复

我们通过在任务执行期间注入随机进程崩溃 (SIGKILL) 来评估 **状态背板** 的恢复性能。

**表 2: 崩溃恢复对比**

| 指标 | 无背板 (Without Backplane) | 有 EdgeSched 背板 |
| :--- | :--- | :--- |
| **恢复耗时** | 7.73 ms | 13.08 ms |
| **恢复任务数** | 0% (0/10) | **100% (10/10)** |
| **状态一致性** | 丢失 | 保持一致 |

**分析**:
- **极低开销**: 基于 mmap 的背板仅增加了约 5ms 的启动时间。
- **零僵尸任务**: EdgeSched 成功识别所有被中断的 "Running" 任务，并在重启时将其标记为 "Failed/Pending"，防止系统误认为任务仍在运行但 Worker 已死锁的 "僵尸" 状态。
- **微基准测试**: 单次状态操作 (注册/更新) 耗时 **< 0.01 ms**，证实持久化层不会阻塞高频调度循环。

## 6.4 系统扩展性与基线对比

我们使用合成负载 (Mock 任务, n=300) 将 EdgeSched 与标准并发模式进行了对比。

**表 3: 基线对比**

| 框架 | 吞吐量 (tasks/s) | P99 延迟 (ms) | 说明 |
| :--- | :--- | :--- | :--- |
| **Naive Async** | 56.37 | 3235.2 | 无限制并发，长尾延迟极高 |
| **Threadpool** | 78.68 | 100.5 | 速度最快，但缺乏 GPU 显存感知 |
| **Semaphore** | 42.95 | 6971.2 | 基础限流，无优先级/恢复机制 |
| **EdgeSched** | **38.07** | **7559.6** | **全功能集 (优先级 + 恢复)** |

**压力测试结果**:
- **负载**: 2000 个任务，200 并发。
- **成功率**: **100%** (无任务丢失)。
- **稳定性**: 持续运行 10 分钟无内存泄漏 (RSS 稳定在 ~581 MB)。
- **开销**: 相比原始信号量方案约 11% 的吞吐下降，是维护优先级队列、任务生命周期和持久化保证的成本。对于可靠性高于原始吞吐的边缘场景，这一权衡是合理的。

---

## 6.5 语义验证

我们验证了对用户体验至关重要的特定调度语义：

1. **取消 (Cancellation)**:
   - **LLM 流式取消**: 平均响应延迟 **50.33 ms**。系统成功在生成中途停止。
   - **图像队列取消**: 平均响应延迟 **1002.17 ms**。排队任务被立即丢弃；运行中任务继续执行但丢弃结果 (软取消)。

2. **优先级反转**:
   - 在混合负载中，HIGH 优先级任务 (如用户聊天) 在分发队列中始终抢占 LOW 优先级任务 (如后台摘要)。

## 6.6 总结

评估表明，EdgeSched 有效解决了 "8GB 显存墙" 问题。它以少量吞吐 (~11%) 和迁移延迟 (~2s 卡顿) 为代价，换取了 **有保证的系统稳定性** (100% 成功率，避免 OOM) 和 **持续的服务可用性** (热切换恢复)。系统可扩展至数千个任务，并在毫秒级内从崩溃中恢复，使其适合生产级边缘 AI 助手。

# 实验阶段与正式矩阵

> 导航：[总索引](README.md) · 兼容入口：[THESIS_EXPERIMENT_GUIDE_DRAFT.md](../THESIS_EXPERIMENT_GUIDE_DRAFT.md)

## 11. 实验阶段划分

### 11.1 探索与校准

探索阶段用于：

- 找到可行驻留档位；
- 确定核心扩展曲线；
- 估计迁移、加载和 KV 代价；
- 校准安全余量、EMA、迟滞和候选配置；
- 排除没有收益的配置。

探索数据可以作为画像图或特性分析，但不能同时用于挑参数和证明主策略优于所有基线。

### 11.2 冻结

正式评测前必须冻结：

- 代码版本和提交哈希；
- 模型文件和哈希；
- 驻留档位；
- 核心候选；
- 安全余量；
- EMA、迟滞和决策规则；
- prompts、TTS 文本、声音配置和随机种子；
- 实验脚本和统计口径。

### 11.3 正式实验

正式实验使用新运行数据和预先冻结的配置。流程为：

\[
Implementation \rightarrow Calibration \rightarrow Freeze
\rightarrow Formal\ Evaluation \rightarrow Paper\ Update.
\]

## 12. 正式实验矩阵

### E0：正确性与真实后端确认

目的：证明实验没有静默回退到 Mock。

检查：

- 真实 Qwen3.5 GGUF 加载；
- 真实 Qwen3-TTS Base 输出；
- 真实 Forge 生成；
- KV 保存恢复；
- 设备与资源采样；
- SM 分区后端、请求比例和实际有效 SM 数验证；
- 取消、队列和失败闭合。

### E1：单模型画像

#### E1-L：LLM

- 驻留档位；
- CPU 核心数；
- 不同 KV / context 长度；
- TTFT、prefill、decode、token gap；
- 显存、内存和转换代价。

#### E1-T：TTS

- 完整 CPU、完整 GPU，以及后端支持时的组件级驻留配置；
- 每个组件配置的明确 device map 与主机/GPU 内存占用；
- 不同物理核心预算；
- 短、中、长句子 chunk；
- TTFA、RTF、资源峰值。

#### E1-D：Diffusion

- 标准 b=1 请求；
- 同 prompt 的 b=2、b=4；
- 不同分辨率与 steps；
- 冷加载和稳态执行；
- 显存时间线。

#### E1-G：GPU 计算份额

- MPS/Green Context 能力 preflight；
- TTS T0/T3 在离散有效 SM 档位下的 TTFA、RTF、显存和输出正确性；
- Diffusion b=1 在离散有效 SM 档位下的延迟、显存和利用率；
- LLM 仅对进入 S0 共享候选的驻留档位补测 SM 曲线；
- 请求百分比、实际有效 SM 数、后端、客户端 CUDA context 创建顺序和异常清理；
- 不受控共享作为必需基线。

### E2：无图像的 LLM→TTS 流水线

通用设计比较 S0-A、S0-B、S0-C(k)，S0-D 仅在可行时加入。当前 small C512 的执行集合以已冻结的具体配置为准：`K24:T0`、`K24:T3`、`K0:T0`、`K24:T4`；不按通用标签补入未验证的 FULL 组合。`K0:T4` 全 CPU 已以负面边界收案，不再进入主矩阵。

同时在 GPU 执行的配置先采用不受控共享；必要时补显存共驻留但计算串行的诊断对照，两者分别标记。静态 SM 分配仅在 E1-G 能力和性能验证通过后加入；当前 SM-B/C/D/E 为 PAUSED，不阻塞 E2。

场景：

- 单轮短回复；
- 单轮长回复；
- 连续多轮语音会话。

指标：

- 第一段文本时间；
- 首句完整波形就绪延迟与首次实际播放延迟（分别记录，不混称 TTFA）；
- 音频 gap / underrun；
- 完整语音回复时间；
- LLM tokens/s；
- 请求/实际有效 SM 数与 SM 配置切换成本；
- 转换成本及其跨轮摊销。

#### 当前 S0 端到端协议草案（待确认，不是冻结协议）

**目的与范围。** 只补四个容量可行配置的真实交互证据，不重跑已收案容量曲线，不实现 planner，不加入 Forge、视觉或 C2048/C4096。当前轮次是静态放置比较，转换次数应如实为零；加载路径另记，动态转换与摊销在后续阶段验收。

**建议主链路。** LLM 流式输出 → 固定规则分句 → TTS 逐句生成完整波形 → 连续播放。允许后续文本生成、当前句合成和已有音频播放重叠；不等待整段文本完成，不把非增量 TTS 称为增量音频后端。首句可播放即启动是建议主策略，预缓冲另作显式对照，尚未冻结。

**先确认再正式运行的参数：**

| 项目 | 必须冻结的内容 | 当前状态 |
|---|---|---|
| 输入与生成 | prompt 集、seed、输出上限、声音、文本正确性/长度核查规则 | 待确认 |
| 分句 | 标点规则、最小/最大句长、尾句 flush、队列顺序 | 待确认 |
| 启动策略 | 首句即播或固定预缓冲量；禁止逐配置调节以掩盖断流 | 建议首句即播，待确认 |
| 首句就绪 SLO | 请求至完整首句波形就绪的截止值及统计口径 | 待确认，不预填数值 |
| 实际播放 SLO | 请求至设备消费首样本的截止值及统计口径 | 待确认，不预填数值 |
| 连续性门槛 | 目标零 underrun 的验收范围、采集分辨率、允许的设备供给提前量 | 待确认 |
| 比较规则 | 主要指标、Pareto 比较容差、失败与超时处理 | 待确认 |

**最小推进顺序。**

1. Pilot：四配置各一条多句回复，检查分句/音频顺序、真实后端、重叠时间线和播放采集。Pilot 只用于协议与采集校准，不混入正式评价。
2. 冻结协议：确认上表，固定输入和分句规则，记录版本与 manifest。不能看完正式结果再调截止或预缓冲。
3. 正式矩阵：四配置 × 短回复/多句长回复/连续会话 × 每格至少五次完整独立运行；按输入与轮次配对，随机或正反交替配置顺序。该最小设计为 60 次场景运行，不是已完成记录。
4. 审核与判定：输出逐请求/逐句原始记录、资源/正确性失败、播放时间线与配对比较，再按第 10 模块 Gate B 判定实现准入；证据不足不得登记 Go。

**公平性与容量边界。** 四配置使用相同输入与生成设置，保存实际生成文本、token 数、分句文本和音频时长；同一 seed 不替代输出一致性检查。输出差异超出预先约定范围时，按冻结规则处理并报告，不能静默删除慢或失败运行。固定文本重放可作隔离诊断，但不能冒充真实 LLM→TTS 端到端结果。

正式长回复或连续会话前，核对冻结 C512 口径对应的输入 tokens、输出/KV 余量和 `n_ctx`。多轮 reset/裁剪策略须统一记录；若无法在已验证边界内形成场景，先缩短场景或另立容量分支，不沿用 C512 阈值外推。

**冷热与统计。** 先独立预热并比较已驻留稳态；需要加载的冷路径单独从请求到达计时，包括真实加载/等待，不能与 warm 合并。运行期间继续保留资源与 swap 门禁，但不重估已冻结阈值。至少五次独立运行不等于足够的请求级 p95 样本；按第 08 模块分别核对请求与 chunk 样本数，保留运行级分组，不把同次运行的 chunk 当独立重复。

**证据产物。** 保存统一单调时钟下的 request、token/句提交、TTS 入队/开始/波形 ready、播放器提交/消费/结束事件及 underrun 记录；保存音频格式、设备缓冲配置和时钟映射。软件提交时间、播放模拟与设备实际消费必须区分。指标定义见第 08 模块；本草案不声称采集器已实现或端到端已通过。

#### E2 实现状态与 pilot 待验证项（2026-09-09，非性能结论）

已实现 `experiments/elastic_residency/s0_pipeline/`（config/events/clock/token_source/tts_executor/playback/runner/s0_child/s0_parent），串起 LLM 流式 → 固定分句 → 有界队列 → 逐句合成 → 连续播放。同进程 TTS 执行器沿用已冻结的放置、加载顺序、核租约与采样骨架，但**不自动继承旧容量矩阵结论**，新执行路径仍须在 pilot 中复核实际资源峰值并继续过资源与 swap 门禁。

静态验证（`tests/elastic_residency/test_s0_pipeline_*.py`，17 项通过，Windows 侧替身）：桥接与队列有界且背压可达、保序、尾句 flush、异常退出落盘、取消后队列无残留、供给不足与自然静音区分、执行区间与提交区间分离。

已明确的口径约束：

- 时间语义：token 交付、线程提交、合成开始、波形就绪、播放提交、设备消费分别记录；`submit` 不得冒充 `execution_start`，callback 时刻不得冒充设备播放时刻，取不到设备时钟时标 `proxy` 并保留说明。
- 时钟分辨率必须记录：Windows `time.monotonic_ns()` 粒度约 15.6 ms，短于一个 tick 的执行区间会被测成 0；pilot 与正式运行应在 WSL2 执行，并在产物中保留 `clock_resolution_ns`。
- 有界性不止 TTS 队列：token 桥接、待播音频句数、正在合成项均需记录深度，否则"队列有界"不等于背压传回 LLM。

pilot 待验证（尚未跑真实模型）：四配置实际资源峰值与 swap；LLM 生成与当前句合成是否真实重叠；实际播放时间与零 underrun 是否可验收；WSL 与 Windows 时钟映射误差。上表七项协议参数**仍全部为 pending**，未冻结。

#### E2 pilot 结果（2026-09-09，run `s0_pipeline_20260909_180109`，只验链路与采集，不下性能结论）

四配置各一条多句回复（128 token 输出上限，20 句）全部完成、`all_passed=true`、swap 门禁全过、保序无乱序、token 桥接打满上限且 `blocked=8~9` 次（背压真实传回 LLM）、TTS 执行区间首尾相接（K24 档句间 gap ≤3.3 ms）。时钟分辨率 551 ns（WSL2），事件 2528 条，执行区间与提交/交付区间已分离。

| 配置 | 首句 TTS 就绪 | 合成总耗时 | 音频总时长 | 最大排队等待 | 最大合成间隙 | 生成×合成重叠 |
|---|---|---|---|---|---|---|
| K24:T0 | 4.14 s | 115.5 s | 66.8 s | 39.5 s | 3 ms | 67.7 s |
| K24:T3 | 4.61 s | 148.1 s | 66.8 s | 52.0 s | 2 ms | 84.1 s |
| K0:T0 | 3.75 s | 132.2 s | 67.3 s | 17.9 s | **5901 ms** | 125.4 s |
| K24:T4 | 13.82 s | 529.7 s | 66.4 s | 203.2 s | 2 ms | 276.2 s |

等待来源判读：K24 三档 `synth/audio ≈ 1.7/2.2/8.0`（RTF 全部 >1.5），积压完全来自**下游合成**；K0:T0 出现 4 次上游供给断档（1.6/3.4/5.7/5.9 s），对应 LLM 全 CPU 生成拖慢交付并与 GPU TTS 抢核，是"共享干扰"的观察形态。K24:T4 全 CPU codec 首句就绪恶化约 3.3 倍，与该档负面边界预期一致。LLM 生成与当前句合成的真实重叠在四配置中均成立。

冻结协议前必须解决的 pilot 观察与待验证解释：

1. **模型直接输出思考过程**（第 0 句为 "Thinking Process:"，后续为 markdown 分析列表）：9B 模型未用 `<think>` 标签，分句器过滤不到。待验证：改写 prompt 明确"直接回答、不写分析过程"，或评估对输出开启思考标签的依赖；两者都属输入冻结项。
2. **markdown 符号被切成句**（"**"、"1."、"\\* Topic:"），其中 "**" 合成出 10.2 s 音频（TTS 对纯符号文本退化）。待验证：prompt 禁止 markdown，或分句规则过滤符号句；两者择一冻结后不得逐配置调整。
3. K0:T0 首次运行 SIGSEGV（退出码 -11）未复现；正式运行继续监控，不作为结论。
4. 播放路径未接入：本轮 `--enable-playback` 关闭，实际播放时间与零 underrun 验收仍为 pending；WSL→Windows 连续流传输未实现。

### E3：Diffusion 期间的语音流水线

比较 S1-A、S1-B(k)、S1-C，S1-D(k) 仅在可行时加入。S1-C/S1-D 必须分别测试显存共驻留但计算串行、不受控并发和受控 SM 分配，不能把三种模式混成一个“共享 GPU”配置。

至少包含：

1. 普通单图请求；
2. 明确标记为压力测试的持续 GPU 占用场景。

指标：

- 图片资源准备和第一张图片时间；
- Diffusion slowdown；
- LLM TTFT、tokens/s 和 token gap；
- TTS TTFA、RTF 和音频断流；
- TTS/Diffusion 的请求与实际有效 SM 数；
- 不受控共享相对受控 SM 分配的尾延迟差异；
- 峰值显存、内存和 CPU 利用率。

### E4：CPU 核心与 GPU SM 分配

候选必须由 E1 推导，不能预先穷举等分组合。

步骤：

1. 求 \(c_T^{min}\)；
2. 测试其邻域；
3. 将剩余核心分配给 LLM；
4. 对最优两个候选做绑核、CCD、SMT 和系统保留核心消融。

随后对需要 GPU 共享的流水线：

1. 求满足 TTS 门槛的最小 \(s_T^{min}\)；
2. 将剩余 SM 分配给 LLM 或 Diffusion；
3. 只在临界点邻域补测，不穷举所有 CPU 核 × SM × 驻留档位组合；
4. 比较 CPU 分核、GPU 分 SM 以及二者联合启用，隔离每个维度的贡献。

### E5：代价感知策略对比

主基线：

| 策略 | 含义 |
|---|---|
| Serial/Wait | 保持当前驻留，竞争任务等待 |
| Always Full Migration | 当前完整 LLM 迁出/恢复策略 |
| Static Best | 使用校准阶段得到的固定最优配置 |
| Uncontrolled GPU Co-run | 显存允许时直接并发，不限制 SM |
| Static SM Split | 使用离线标定得到的固定 SM 份额 |
| Pareto-Only Instantaneous | 枚举当前 SLO-feasible 配置，Pareto 过滤后按固定字典序选择；不看转换成本或队列视界 |
| Transition-Cost-Aware | 只对当前 phase 比较收益与转换成本，不累计已经到达的后继工作 |
| Queue-Horizon-Aware EdgeSched | 在已经到达的 phase/queue 视界内累计收益，联合选择驻留、CPU 核、SM、batch 和转换方式，并受最小驻留窗口约束 |
| Oracle | 使用真实未来执行时长进行事后最优选择 |

迁移机制基线可保留：

- Cold Restart；
- Symmetric Migration；
- Urgent Down + Atomic Hot-Swap Up。

这些基线回答的是状态转换机制问题，不能替代新版在线规划策略基线。正式比较必须分别报告
SLO、端到端完成时间、吞吐、转换次数、真正完成 payback 的转换比例，以及相对 oracle 的
decision regret。Pareto-only 是可解释的决策基线，不单独作为 EdgeSched 的算法贡献。

### E7：真实 N 阶段工作流

至少使用：

\[
ASR/RAG\rightarrow LLM\rightarrow TTS+Image.
\]

ASR/RAG 可以轻量，但必须是真实执行。Mock N-phase 实验保留为调度语义测试，不作为真实性能结果。

### E8：消融与稳健性

消融：

- 无时长预测；
- 无在线 EWMA 残差修正，只使用离线画像插值；
- 无 queue horizon，只看当前 phase；
- 无 transition cost，退化为 Pareto-only instantaneous；
- 无 minimum residency window；
- 禁用 `PARTITIONABLE`，将相关阶段退化为完整设备配置；
- 无CPU核心隔离；
- 无 SM 分配，退化为默认 CUDA 不受控共享；
- 固定 SM 分配，不根据工作流状态或画像调整；
- 无驻留迟滞；
- 无KV保存；
- 固定设备放置。

敏感性：

- KV / context 长度；
- TTS chunk 长度；
- Diffusion 时长；
- 图像队列深度；
- 预测误差；
- predictor 的画像覆盖率、MAPE、绝对误差 p95 与 decision regret；
- 显存安全余量。
- SM 分区粒度与 TTS 最小有效 SM 数；
- GPU utilization 或带宽压力预测误差。

泛化不能只由 phase 接口的抽象命名证明。主链路通过后，正式 evaluation 至少覆盖两个变化轴，
并尽量包含一个替代模型或后端实例：LLM 规模/context、TTS backend/chunk 数、GPU burst 类型或
Diffusion 参数、queue depth/burst arrival pattern、co-runner/冷热状态。所有变化必须复用相同的
phase/profile/PlacementPlan 接口，不能为新模型增加专用调度分支。

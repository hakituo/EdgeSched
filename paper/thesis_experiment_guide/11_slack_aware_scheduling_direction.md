# 论文主线候选：余量感知的驻留调度

> 导航：[总索引](README.md) · [当前门禁](10_gates_and_current_status.md)

> **状态（2026-10-26）**：方向草案，已与用户确认按此方向验证。本模块只依据已有产物做离线复算，

## 1. 为什么换主创新点

调度器论文的主创新点必须是调度算法。现有公式稿（`../edgesched_phase_aware_formulation.tex`）的规划器只回答
"每个模型放在哪"：从验证过的有限配置集里取 Pareto 前沿、按字典序选择、再用迟滞决定是否切换。
实测数据表明，这个维度几乎没有选择空间：

- **只有对话（S0）时**：给 LLM 的 GPU 层越多越好，`K24:T0` 全面占优，答案几乎是确定的；
- **有图像任务时**：16 GB 主机内存下 LLM+Forge 没有任何可共置档位（4B 和 9B 一致，见第 10 模块 H_D 收案），
  可选项被主机内存直接砍光。

好算法和朴素算法会选出同一个答案，这是 Gate B 拿不到收益的结构性原因。收益空间应该在**时间维度**：
什么时候切换、各阶段按什么顺序使用 GPU。

## 2. 核心思想

交互流水线的**生产远快于消费**：音频合成完以后，用户还要听一段时间；听完以后还要开口说话、经过 ASR。
在这两段时间里，本轮回复已经不需要 GPU。

> 在模型无法完整共驻留的设备上，把**播放余量**（已合成未播放的音频）和**对话轮次间隙**当作可调度的资源，
> 把高代价的驻留切换和 GPU 突发任务（图像生成、视觉编码）安排进去。

对照策略：

| 策略 | 预期问题 |
|---|---|
| 等说完再执行突发任务 | 音频连续，但突发任务要多等一整段播放 |
| 立即二元迁移（LLM 退到 CPU） | `K0:T0` 已测：首句 10.7 s、断流明显 |
| 不受控共跑 | 见下文 E4：共跑减速约 4 倍 |
| **余量感知调度**（本文） | 先尽快生产，余量足够覆盖"逐出 + 突发 + 恢复"时再交出 GPU，余量耗尽前恢复 |

与实时调度中的 slack stealing 有渊源；新的约束是：模型无法共驻留、切换代价以秒计、可行性同时受 GPU 和主机内存约束、
阶段之间有依赖。与 HorizonServe 等工作的差异：它们假设模型已经共驻留，只分配 SM。

| # | 发现 | 数值 | 来源 |
|---|---|---|---|

| E4 | **共跑时 LLM 比隔离画像慢约 4 倍** | K24：3.43 tok/s（v2）对 14.0；K0：1.20 对 4.84；v1 同样 4.8–5.1 倍 | S0 v1/v2 正式批次 vs C2/C3 C512 |
| E5 | 共跑期间 TTS 队列始终为空 | v2 `K24:T0` 的 `tts_queue_depth` 2363 次快照全为 0；TTS 空闲时 LLM 也只有约 4 tok/s | S0 v2 `queue_snapshot` |
| E6 | 合成后余量约 10 s | v2 `K24:T0` 五轮 9.8–12.2 s，中位 10.8 s | S0 v2 事件时间线（callback 代理口径） |
| E7 | 盈亏平衡处在临界 | 假设逐出 0.5 s + 画图 5.2 s + TTS 恢复 5.6 s = 11.3 s，五轮仅 1 轮放得下（余量差 −1.5 至 +0.9 s） | 同上，`--burst-s 5.2 --evict-s 0.5 --restore-s 5.6` |

解读边界：

- E4/E5 说明 S0 的整条流水线卡在 LLM 上，而且不是背压造成的。原因**尚未诊断**：同进程的 GIL 争用、
  28 个 llama 线程与 torch/TTS 线程超额订阅 CPU、或两个环境的 llama.cpp 构建不同，都可能导致这个结果。
  这本身就是一个调度问题（CPU 核预算、阶段串行化），也说明**隔离画像会把共跑性能高估约 4 倍**，
  任何基于画像的规划器都必须先处理它。
- E6 的余量用 callback 代理的首播时刻加音频时长推算，设备时钟未验证；缺音补零时名义播放结束不等于实际结束。
- E7 的 5.6 s TTS 恢复是**假设值**：权重保留在主机内存时搬回 GPU 约 1 s，加上重新捕获 CUDA Graph 约 4.6 s。
  必须由 V1 实测替换。如果只能冷启动（11–16 s），单轮回复内的余量放不下，只能利用对话轮次间隙。
- 如果消除 E4 的减速，LLM 生成 80 token 只需约 6 s，合成可以更早完成，余量会明显变大。这是**推测**，需要 V0 验证。

### 3.1 V0 结果（2026-10-26，原生 Linux 真实运行）

探针 `experiments/elastic_residency/colocation/`（`v0_parent.py` 编排，每个单元一个独立子进程），
产物 `experiment_results/elastic_residency/colocation_v0/colocation_v0_20261026_v1|v2/`。
9B K24、C512、S0 同款 prompt 与模板，LLM 绑 14 个物理核（28 个逻辑 CPU），每单元预热 1 次 + 正式 3 次；
**所有单元的输出完全相同**（81 token、同一哈希），不存在输出差异带来的协变量问题。

| 单元 | LLM tok/s（中位，范围） | TTS RTF | 说明 |
|---|---|---|---|
| alone（28 线程） | 9.7（6.6–11.7） | — | 28 线程占满逻辑核，单独跑也不稳定 |
| alone_t14 | **13.1**（12.4–13.2） | — | 与 C2 画像 14.0 接近 |
| tts_idle | 7.8 | — | 仅驻留，约 1.25 倍 |
| tts_thread（S0 同款） | **0.83** | 0.34 | 约 11.7 倍减速 |
| tts_thread_torch1 | 0.82 | 0.34 | torch 线程无关 |
| tts_proc_overlap | 0.83 | 0.34 | 分进程但共用核：**不是 GIL** |
| tts_proc_disjoint（28 线程） | 4.3（3.4–5.4） | 0.38 | 核不重叠，但 28 线程仍偏多 |
| tts_thread_t14 | 6.85 | 0.41 | 只降线程数 |
| tts_proc_disjoint_t14 | **7.81** | 0.42 | 核不重叠 + 14 线程：只剩 GPU 争用 |
| tts_alone | — | 0.33 | TTS 自身基线 |

判读：

- **主因是 CPU 线程超额订阅**：llama.cpp 的 28 个线程每层都要互相同步，占满全部逻辑核后，TTS 的主机线程
  一插进来，整组线程就被最慢的那个拖住（约 8 倍）。降到每个物理核一个线程即可消除。
- **剩下约 1.7–1.9 倍是 GPU 争用**（13.1 → 6.85–7.81），换核、换进程都去不掉，这才是调度算法要处理的部分：
  同时跑、串行跑，还是用 MPS 分 SM。TTS 被拖慢约 25%（RTF 0.33 → 0.41–0.42），仍有实时余量。
- **V0 放行**：共跑速度恢复到隔离的 60%（7.81/13.08），满足第 5 节"50% 以上"的条件。
- 连带影响：历史 C2/C3 画像和 S0 都用了 28 线程。S0 必须用 14 线程重跑，才能重新判读余量（E6/E7 会变）；
  论文里"隔离画像高估共跑性能"这一条，应改写为"线程配置不当会让共跑性能塌陷一个数量级，而正确的核预算之后，
  仍剩约 1.8 倍的 GPU 争用"。

## 4. 口径：16 GB 是主机内存预算，不是机器的物理内存（2026-10-26 用户确认）

16 GB 是给整套本地 AI 服务的**主机内存预算**，与机器装了多少内存无关：

- 16 GB 的服务器或小主机可以直接部署；
- 32 GB 的个人办公电脑上，它在后台运行，同时留出一半内存给用户正常工作；
- 128 GB 的机器也同样受益：多出来的内存属于用户的其他工作，不应该被一组本地模型吃光。

因此论文把主机内存写成与 GPU 显存并列的**资源预算** \(V_{host}=16\,\mathrm{GB}\)，而不是硬件规格。
原生 Linux（30 GB 物理内存）上的正式实验必须用 cgroup 强制这个预算
（例如 `systemd-run --user --scope -p MemoryMax=16G -p MemorySwapMax=...`），并把预算、实际上限与 swap 设置写进 manifest。
WSL2 时期的 H_D 负面边界正是在 16 GB 下得出的（20 GB 诊断 3/3 通过，证明根因是主机内存容量），与这个口径一致，可以继续沿用；
但原生 Linux 上的页缓存与回收行为和 WSL2 不同，涉及主机内存的边界需要在 cgroup 预算下复测。

## 6. 论文骨架（候选）

- **主张**：在模型无法完整共驻留的 8 GB 级设备上，余量感知的驻留调度让图像等突发任务能插入语音交互，同时保持音频连续，
  在突发任务延迟与音频连续性上优于等待、二元迁移和不受控共跑。
- **贡献 1（动机，已有证据）**：无法共驻留的区间真实存在（主机内存是绑定约束）；后端实时余量决定放置有没有意义（v1/v2 结论反转）；
  隔离画像会把共跑性能高估约 4 倍（E4）。
- **贡献 2（主创新）**：余量感知调度算法，包括余量的定义、切换可行条件，以及每个事件点对操作顺序的求解（阶段少，可精确搜索）。
- **贡献 3**：真实系统实现，在混合请求轨迹上评估，并与 oracle 比较。

现有 S0 结果转为动机章节和 S0 模式的基线；主评估转到指南早已定义、但尚未测过的 S1/S2。
